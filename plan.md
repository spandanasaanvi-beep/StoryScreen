# StoryScreen — Implementation Plan

## Scope and implementation approach

Extend the existing React, TypeScript, and Vite StoryScreen in place. Preserve the current interactive story library, branching player, history, accessibility settings, and cinematic design. Add a distinct Story-to-Video Studio as the prominent landing-page path: **Create Your Story → choose one of eight genres → answer only that genre's questions → review a generated script → render a real MP4 → watch, replay, download, or create another story.** Keep the older custom interactive-adventure form available at its own route so no working feature is removed.

The browser calls same-origin `/api/generate-story` and `/api/render-video` endpoints. In production, a small Node HTTP server serves the Vite `dist/` output and those endpoints on `PORT` (3000 default); in development, a small Node process listens on 3001 and Vite on the existing Preview port 3000 proxies `/api` to it. No database or user account is introduced. Persist generated scripts and MP4 Blob records in IndexedDB; give the user a download control because browser quota and storage support vary.

Story drafting first attempts the built-in Manus OpenAI-compatible chat service from Node using runtime-only `MANUS_API_URL` and `MANUS_API_KEY`. The prompt requests a bounded JSON script (title, logline, 3–6 narrated scenes, concise visual notes); parse and validate all fields, scene counts, text sizes, and allowed visual IDs before using it. Never send the server credential to the browser, build output, logs, or a story result. If the service is absent, times out, rejects the request, or returns invalid content, create an input-specific deterministic script locally and show which provider was used. The UI makes AI use explicit; the same core video flow works without the service or any third-party key. Automated and end-to-end development tests use the local fallback and mocked provider tests, not a live model request.

Render a genuine MP4 locally with FFmpeg from scene-specific narration/captions and curated 16:9 genre artwork. Apply per-scene slow pan/zoom, selected aspect ratio/color treatment, title overlays, and burned-in subtitles; use eSpeak-NG for selected language/voice narration when available. If speech synthesis fails, continue with subtitle-only MP4 and report the audio state. This is a rendered illustrated-story video, not AI-generated continuous-motion footage; no video-generation API or key is required. The UI uses stable `/manus-storage/` image paths returned by the managed image service. The server maps genre IDs to allowlisted storage object keys and uses authenticated presigned GET requests to fetch their bytes for FFmpeg; signed URLs stay in server memory and never enter browser data or logs. No user-supplied URLs or filesystem paths enter FFmpeg. If managed artwork is unavailable, use a rendered gradient/title/subtitle fallback and still return only a valid completed MP4. Bound input sizes and durations, use temporary work directories, invoke child processes without a shell, time out rendering, and clean temporary files.

Use short, useful progress states only while actual story generation or FFmpeg rendering is in progress. Do not report success until the server has produced a nonempty, probeable MP4. The dedicated video route uses a real HTML video element and offers Play/Pause, Replay, Download, and Create Another Story. Keep rendering retry available with the same approved script and parameters.

The app's existing React and TypeScript dependencies remain minimal; API and renderer use Node built-ins plus packaged system tools, not a database, framework, or external video provider. The Docker image installs the pinned Node dependencies, FFmpeg, eSpeak-NG, and a font; builds the frontend; starts the Node application; and exposes an unauthenticated `/api/health`. Preserve the existing static `build` declaration for the `dist/` half, add a container `deploy` declaration, and order published `/api/*` to `server` before the static `/*` SPA fallback. Keep `runtime.port` at 3000 and auto-publishing off; prepare the project for a future publish but do not publish it in this task.

## Project structure

- `src/App.tsx`: existing custom router and interactive-story shell, plus the new studio and `/video/:videoId` route.
- `src/screens/`: existing Home/Library/Create/Player/Ending/History/Settings; new genre selection, genre-input/script review, and generated-video player screens.
- `src/videoStudio/`: genre-question catalog, typed generation/video contracts, API client, request/progress state, and form validation.
- `src/state/videoStorage.ts`: versioned IndexedDB storage for scripts and playable MP4 Blobs with failure handling.
- `src/components/`: reuse the current brand and focusable controls; add reusable genre cards, step progress, and video status/player controls without changing the visual system.
- `server/index.ts`: bounded HTTP/JSON request handling, `/api/health`, story and render routes, and secure production static/SPA serving.
- `server/storyGenerator.ts`: runtime Manus chat call, deterministic genre-specific script fallback, parsing, validation, timeouts, and mockable provider boundary.
- `server/videoRenderer.ts`: allowlisted project-storage object keys, presigned asset downloads, eSpeak-NG narration, subtitle generation, safe FFmpeg invocation, MP4 probing, and temp-file cleanup.
- `scripts/dev.mjs`, `vite.config.ts`: coordinate the dev API/Vite processes and proxy `/api` without changing the configured Preview port.
- Managed image assets: retain the existing fantasy/mystery/science-fiction art and add five matching image generations for comedy, adventure, mythology/folktales, bedtime, and inspirational stories; store only stable `/manus-storage/` paths in app source.
- `public/manus-routes.json`: all user-visible page patterns, including interactive screens and generated-video route; exclude API routes.
- `Dockerfile`, `.dockerignore`, `README.md`, `.env.example`: container build/runtime, local setup, service/secret policy, fallback behavior, exact video output scope, and limitations.
- `tests/`: typed UI/genre and storage helpers plus Node unit tests for input validation, LLM adapter/fallback, and video output probing.

## Design direction

**Movement:** cinematic streaming-interface design with a storybook-illustration sensibility. **Core principles:** a cinematic focal point, generous spacing and readable large controls, consequence-led storytelling, and clear remote focus. **Color philosophy:** near-black ink and midnight navy frame bright lantern gold, lunar silver, and restrained Mars amber/green; color signals story mood and selected focus rather than decoration. **Layout paradigm:** a widescreen hero composition with offset narrative copy and a horizontal story rail, then focused, spacious screen layouts instead of dense card grids. **Signature elements:** a luminous portal/halo brand mark, layered cinematic story art, and a thin warm-gold focus outline with a soft glow. **Interaction philosophy:** every action is a deliberate, clearly focused choice; directional movement is predictable and primary actions are large. **Animation:** short, low-amplitude fades and parallax-like shifts; no rapid movement; honor reduced-motion settings. **Typography:** elegant editorial serif titles paired with a clean high-legibility sans serif for controls and long text, using local/system fallbacks without a remote-font dependency. **Brand essence:** a family-friendly interactive story player where choices reshape the tale; curious, cinematic, welcoming. **Brand voice:** evocative, concise prompts; examples: “Step into the story.” and “The next chapter is yours to shape.” **Wordmark/mark:** a simple original portal/lantern glyph beside the StoryScreen wordmark. **Signature brand color:** lantern gold.

The original fantasy, mystery, and science-fiction assets remain. Five new wide illustrations extend the same painterly midnight palette to comedy, adventure, folklore/mythology, bedtime, and inspiration. Keep important visual subjects away from subtitle and title safe areas; do not embed text in images.

## Material constraints

The hybrid Node server is now required for trusted Manus AI credentials, managed-image downloads, and actual media rendering; the project already has `features.server: true`. No managed database, login, third-party AI account/key, or remote video-renderer API is required. The built-in Manus story request is optional and protected server-side; it can consume the platform's AI service, so development tests deliberately use the deterministic path instead of making a live generation call. FFmpeg/eSpeak-NG are installed in the production image; local development must have them installed or use the subtitle-only fallback. The app renders animated still illustrations with audio/captions, not model-generated moving footage. Browser IndexedDB storage is per device and quota-limited; MP4 download is the durable user-owned option. Fire TV hardware and a published production instance are not tested. Automatic publishing is false; do not publish or enable it.
